Пользователь разрешил публикацию 18 ноября 2026 года. Целевой адрес: https://176.98.179.224. Репозиторий: https://github.com/lolipokzz/ai-challenge-coding. Данные на сервере демонстрационные; локальная база с компьютера не переносится.

## Автоматическое обновление

Workflow `.github/workflows/deploy.yml` запускается для push в `main`, pull request в `main` и вручную из GitHub Actions. На pull request выполняются только проверки и сборка. Публикация доступна только для `main`, после успешных проверок.

1. Установить зависимости по `pnpm-lock.yaml` через pnpm 10.11.0 на Node.js 22.
2. Выполнить HTTP-тесты Python, `go vet` и проверку синтаксиса скриптов. Go выбирается как актуальная стабильная версия.
3. Собрать React и Go-бинарник для Linux amd64 без CGO. Записать SHA коммита в `dist/version.txt`.
4. Передать архив по SSH пользователю `razumist-deploy`. Доверенный ключ сервера проверяется по `DEPLOY_KNOWN_HOSTS`.
5. Проверить архив, создать отдельный каталог релиза, сохранить резервную копию SQLite, переключить симлинк и перезапустить только `razumist.service`.
6. Проверить локальный HTTP API и SHA релиза. При неуспехе вернуть предыдущий релиз. Затем Actions проверяет SHA через публичный HTTPS.

Приложение работает отдельным пользователем `razumist`, а сборка выполняется на GitHub, чтобы не перегружать сервер с 1 ГБ RAM. Публикации одной ветки выполняются последовательно. Первые запуски до появления базы создают два стандартных демо-аккаунта.

## Секреты и доступ

В GitHub Settings → Secrets and variables → Actions используются два repository secret:

- `DEPLOY_SSH_KEY`: отдельный Ed25519-ключ для публикации, не пароль root.
- `DEPLOY_KNOWN_HOSTS`: проверенный публичный ключ SSH сервера.

Закрытые ключи и пароли не входят в репозиторий. Ключ публикации ограничен принудительной командой `deploy <SHA>` и не позволяет интерактивный shell, туннели или пересылку агента. Пользователь деплоя может вызвать через sudo только проверяющий аргументы скрипт активации. Конфигурации systemd, Nginx и привилегированные скрипты обновляются администратором отдельно от обычного CI/CD.

## Файлы сервера

| Путь | Назначение |
|---|---|
| `/srv/razumist/releases/<SHA>` | Бинарник и frontend конкретного релиза |
| `/srv/razumist/current` | Симлинк активного релиза |
| `/var/lib/razumist/razumist.sqlite3` | Постоянная база, не перезаписывается релизом |
| `/var/backups/razumist` | 14 последних согласованных SQLite-копий |
| `/etc/nginx/sites-available/razumist` | HTTPS-прокси и HTTP challenge |
| `/etc/systemd/system/razumist.service` | Непривилегированный сервис приложения |
| `/opt/razumist-certbot` | Изолированная установка Certbot |

Старые каталоги релизов автоматически не удаляются: перед ручной очисткой нужно сохранить активный и хотя бы один предыдущий релиз. `data/`, `bin/`, `dist/` и локальные секреты не публикуются в Git.

## HTTPS и резервные копии

Nginx направляет HTTP на HTTPS. Go слушает только 127.0.0.1:8000 и использует `--public-origin https://176.98.179.224`, поэтому cookie получает Secure, а Origin проверяется по явному адресу.

Сертификат IP выдан Let's Encrypt через профиль `shortlived`. Проверка необходимости продления запускается каждые шесть часов с небольшой случайной задержкой. После успешного продления Nginx перечитывает сертификат. Используется webroot, остановка сайта для продления не требуется. Первый сертификат действителен до 24 ноября 2026 года; дальнейшие даты зависят от автопродления.

`razumist-backup.timer` делает ежедневную копию через SQLite Backup API; такая же копия создаётся перед переключением релиза. Копии находятся на том же сервере и не защищают от потери всего диска. Внешнее хранилище резервных копий не подключено.

## Обслуживание

Администратор может проверить:

```sh
systemctl status razumist nginx
systemctl list-timers 'razumist*'
journalctl -u razumist -n 100 --no-pager
curl --fail https://176.98.179.224/version.txt
/opt/razumist-certbot/bin/certbot certificates
```

Ручной откат к существующему релизу:

```sh
sudo /usr/local/sbin/razumist-activate <40-символьный-SHA>
```

Откат возвращает приложение, но не заменяет базу устаревшей копией. При будущих несовместимых миграциях нужен отдельный план восстановления. Для восстановления SQLite остановить сервис, сохранить текущие файлы базы/WAL/SHM, восстановить проверенную копию с владельцем `razumist` и правами 0600, затем запустить сервис. Не заменять базу при работающем процессе.
